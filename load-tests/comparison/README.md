# Сопоставимое тестирование двух реализаций

Для текущей серии **smoke + capacity + stress + spike, по два повтора на каждую реализацию за примерно три часа**, использовать [COURSE_PLAN.md](COURSE_PLAN.md) и `course-suite.sh`. Ниже сохранена подробная методика и отдельный runner для дополнительных экспериментов.

Один и тот же k6-код обращается к общему HTTP API монолита и микросервисов.
Нагрузочные замеры готовятся для самостоятельного запуска в WSL.
Код банковских приложений и их обычные docker-compose.yml не изменены.

## Сначала: общий smoke

Остановить обычные стенды и другие контейнеры, которые используют ресурсы той же WSL VM.
Runner проверит это; сам чужие контейнеры не останавливает.

```bash
cd /home/basybemoog/bank_proto_microservice

bash load-tests/comparison/run.sh mono smoke
bash load-tests/comparison/run.sh micro smoke
```

Если путь монолита отличается, задать `MONOLITH_DIR=/полный/путь`.
Нужны Docker Compose, k6, Python 3, curl, git и tar в WSL.

Каждый запуск собирает отдельный образ, создаёт стенд `bank-course-comparison`,
проходит общий smoke и сверяет БД. HTTP-вход — `http://127.0.0.1:18080`.
Рабочие БД обычных проектов в этом стенде не используются.
Перед smoke и каждой ступенью удаляются **только помеченные тома этого тестового проекта**.
В конце стенд остаётся запущенным для осмотра.

Smoke проверяет регистрацию, вход, создание счёта, чтение, transfer/payment,
комиссии, completed, запрет чужого списания, нехватку средств и нулевую сумму.
Проверка БД отдельно подтверждает сохранность денег и баланс каждого счёта по журналу.
Повтор Idempotency-Key исключён: у монолита нет такой возможности.

## Блокер, обнаруженный в монолите

После переводов монолит не удаляет кеш списков счетов пользователей.
Этот кеш содержит баланс и живёт 300 секунд.
Smoke сначала заполняет кеш, затем переводит деньги и проверяет свежесть GET /accounts.

При устаревшем балансе `read_after_write_fresh = 0`.
Smoke сохранит этот результат отдельно от остальных проверок.
Смешанная нагрузка mixed по умолчанию остановится: сначала нужно исправить
инвалидацию списков счетов **обоих** пользователей после transfer и payment.

Разведочный замер существующих реализаций разрешён явно:

```bash
ALLOW_STALE_READS=1 REPEATS=1 RATES="250 500 1000 1500 2000" \
DURATION_SECONDS=30 WARMUP_SECONDS=10 \
bash load-tests/comparison/run.sh mono mixed
```

Он помечается `api_read_after_write_fresh=false` в JSON и CSV.
Такой результат показывает производительность текущей реализации с устаревшими
ответами; он не доказывает преимущество архитектуры при одинаковой свежести данных.
Для окончательного сравнения mixed требуется свежий smoke на обеих версиях.
Read можно сравнивать на чистых данных без записей; transfer/hot не читают кеш
списков в измеряемых операциях. Их runner разрешает запускать, сохраняя отдельную
метку отсутствия общей гарантии свежести после записи.
Причины и остальные различия перечислены в [REVIEW.md](REVIEW.md).

## Матрица экспериментов

| Сценарий | Одна измеряемая итерация | Данные |
|---|---|---|
| read | GET /accounts | 200 пользователей, по одному счёту |
| transfer | POST /transactions: 70% transfer, 30% payment | те же 200 пользователей |
| mixed | 70% GET /accounts, 30% POST /transactions | те же 200 пользователей |
| hot, дополнительный | только записи, те же типы | 20 пользователей |

Каждый перевод — **1.00 рубль**, комиссия — 0.01 либо 0.03 рубля.
Новые счета открываются с 20 000.00 рублей на обоих стендах.
Это требование общего тестового профиля; setup проверяет фактический баланс.

Выбор операции, отправителя, получателя и типа зависит от SEED и номера итерации
сценария, а не от номера VU или Math.random(). Отправитель и получатель различаются.
На каждую запись передаётся новый ключ; повторов и async-запросов нет.
Регистрация и вход выполняются последовательно в setup, вне измеряемых метрик.
История не включена в нагрузочную матрицу: реализации возвращают разные объёмы
данных при одинаковом запросе. В smoke история содержит ровно две успешные операции.

Прогрев использует min(RATE, 100) операций/с (настраивается WARMUP_RATE).
Он обязан завершиться без отказов и dropped; иначе ступень INVALID.
Небольшая одинаковая нагрузка прогрева позволяет подготовить кеш и соединения,
не создавая очередь уже на предполагаемой границе насыщения.
После прогрева выделяется отдельное время на
завершение запросов; только затем начинается измерение.
Предельное время запроса — 10 секунд, gracefulStop — 11 секунд,
начало measure — через WARMUP + 12 секунд.
Прогрев и measure не имеют одновременно работающих клиентских итераций.
Если сервер продолжает запрос после клиентского таймаута, прогрев не проходит
проверку успешности; такую ступень нельзя считать валидным замером.
Смысл gracefulStop описан в [документации k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/graceful-stop/).

## Равные ресурсы основного стенда

| Ресурс | Монолит | Микросервисы |
|---|---|---|
| Go CPU | 4 | 4 сервиса × 1 |
| PostgreSQL CPU | 4.5 | 3 БД × 1.5 |
| Redis CPU | 0.5 | 0.5 |
| Суммарный CPU quota | **9** | **9** |
| Go память | 2 GiB | 4 × 512 MiB |
| PostgreSQL память | 3 GiB | 3 × 1 GiB |
| Redis память | 512 MiB | 512 MiB |
| Суммарная память | **5.5 GiB** | **5.5 GiB** |

Основной вход: один процесс монолита / один gateway напрямую, без nginx.
Одинаковы образы PostgreSQL 16, Redis 7.4, отсутствие Redis persistence,
уровень логирования warn, сборочный Go image и флаги компиляции.
Go toolchain закреплён внутри сборки; его версия сохраняется в build.log.
TTL кеша списка счетов — 300 секунд (нативный монолита, явно заданный micro).

Это сравнение **реализаций при одинаковом суммарном бюджете**.
Разделение этого бюджета, число БД, пулы, Redis-клиенты, стратегия блокировок,
сбор комиссий и сага различаются; вывод «ускорение только благодаря gRPC»
из него сделать нельзя. Пулы монолита используются с его текущими pgx defaults,
micro — с явными 20/32/32 соединениями.
Настройки отражены в сохранённом Compose и снимке исходников.

Ограничение CPU — потолок контейнеров, а не резервирование ядер.
На машине с 12 логическими CPU остаётся номинальный запас для генератора;
проверить его по telemetry.jsonl. Если WSL доступно меньше 12 CPU или мало памяти,
сначала изменить **оба** профиля симметрично либо вынести генератор.
Не менять лимиты между сравниваемыми повторами.

## Порядок замеров

1. Общий smoke обоих вариантов; устранить функциональные блокеры.
2. Разведка mixed: один повтор, 30 секунд измерения, одинаковые RATE на обоих вариантах.
3. Выбрать общую сетку вокруг границ прохождения и повторить её минимум три раза
   с 60 секундами измерения. Сетка и настройки одинаковы для обоих вариантов.
4. Отдельно выполнить read и transfer на общей сетке: это помогает понять,
   какая часть смешанной нагрузки ограничивает систему.
5. Hot, nginx/масштабирование и сбои — отдельные эксперименты после основной матрицы.

Пример разведки после исправления smoke:

```bash
REPEATS=1 RATES="250 500 1000 1500 2000" DURATION_SECONDS=30 WARMUP_SECONDS=10 \
bash load-tests/comparison/run.sh mono mixed

REPEATS=1 RATES="250 500 1000 1500 2000" DURATION_SECONDS=30 WARMUP_SECONDS=10 \
bash load-tests/comparison/run.sh micro mixed
```

Пример подтверждения (сетку уточнить по разведке):

```bash
REPEATS=3 RATES="500 750 1000 1250 1500" \
bash load-tests/comparison/run.sh mono mixed

REPEATS=3 RATES="500 750 1000 1250 1500" \
bash load-tests/comparison/run.sh micro mixed
```

Заменить `mixed` на `read` и `transfer` для остальных основных сценариев.
Для контроля дрейфа стенда чередовать серии mono/micro, затем micro/mono;
можно использовать REPEATS=1 и хранить каждую серию отдельной папкой.
Каждая ступень получает чистую БД и новое setup. Данные не переходят между RATE.
Сборка образов выполняется один раз на вызов runner.
После измерения есть пауза 60 секунд для завершения запросов, recovery и сверки;
она не включается в измеряемую задержку.

## Метрики и правила прохождения

Для основной фазы сохраняются:

- offered RATE, started, completed, dropped;
- completed_in_window / DURATION — ответы, завершившиеся внутри измеряемого окна;
- completed / max(DURATION, время последнего завершения) — скорость когорты с учётом drain;
- completed / DURATION — отдельный счётчик завершений на секунду заданного окна, не фактический RPS при длинном drain;
- drained_completions — ответы после границы окна;
- p50/p95/p99 всех ответов и отдельные p99 чтений/записей;
- доля успешных бизнес-операций и доля завершённых переводов;
- HTTP-коды, бизнес-отказы, ошибки транспорта, 5xx, OUTCOME_UNKNOWN;
- CPU/RAM контейнеров **этого проекта**, CPU/RSS k6 и ожидания PostgreSQL;
- сверка суммарных денег, индивидуальных балансов и журнала саги;
- сверка количества счетов и границ числа completed в БД: не меньше подтверждённых
  клиенту переводов и не больше всех отправленных попыток (неизвестные исходы могут завершиться позднее).

`PERF_PASS` означает: полный запуск, корректная сверка БД, >=99% завершений
внутри окна, >=99% корректных успешных ответов в целом и по каждому типу операции,
>=99% успешных переводов для write/mixed, <=1% HTTP ошибок,
<=0.5% dropped, p99 <=500ms в целом и по каждому типу операции.
SLO и проценты здесь — заранее выбранные критерии эксперимента, не требования банка.
`PERF_PASS` отдельно от свежести API: без true в соответствующей колонке нельзя
объявлять одинаковую корректность после записи и использовать mixed как окончательный.

| Статус | Значение |
|---|---|
| PERF_PASS | критерии производительности выполнены; проверить колонку свежести |
| SLO_FAILED | превышена задержка/ошибки или не хватает успешных ответов внутри окна |
| LOAD_NOT_DELIVERED | не доставлена заданная нагрузка: VU bound, генератор либо задержки системы |
| CORRECTNESS_FAILED | найдены расхождения балансов/журнала/подтверждённых операций |
| RECONCILIATION_UNAVAILABLE | проверка БД не выполнена; это не доказательство потери денег |
| INVALID | прерывание, OOM/ошибка k6, неполный интервал или отсутствующие метрики |

512 VU для измерения и 128 для прогрева заданы заранее и ограничены сверху.
При нехватке VU нельзя автоматически объявлять найденным максимум сервера:
[k6 может терять итерации из-за отсутствия свободных VU](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/).
Оценить CPU/RAM генератора и повторить обе версии с одинаковым новым VUS.
Идентификатор итерации берётся из [k6/execution](https://grafana.com/docs/k6/latest/javascript-api/k6-execution/).

«Устойчивая пропускная способность» — максимальная проверенная ступень,
которая проходит все выбранные повторы; для mixed нужны также свежие ответы.
Это нижняя оценка по сетке, не точный физический максимум.
Для отчёта показывать диапазон/медиану повторов, а не лучший единичный запуск.
Пулы и ожидания помогают сформировать гипотезу причины; для доказательства
конкретного bottleneck нужен отдельный контролируемый эксперимент.

## Результаты и последующая передача

Папка: `load-tests/results/comparison/<target>-<workload>-<time>-<pid>/`.

В корне: summary.csv, resolved Compose, версии, сведения о хосте,
commit/status/diff, исходники обоих проектов, SHA256 набора сценариев.
В smoke: summary.json, код выхода и сверка.
В каждой ступени: summary.json, result.json, run.json, k6.log, telemetry.jsonl,
containers/images.json, pg-before/after.json, reconciliation.json, service-logs.txt.
При микросервисах дополнительно reconcile.txt.
CPU/RAM/PG raw telemetry собирается во время setup, прогрева и измерения. Окна считаются по прогрессу executor k6; календарная привязка приблизительна при сдвиге системных часов, который фиксируется в wall_clock_drift_ms. При drain скорость когорты является оценкой по нижней границе HTTP-времени; основная метрика полезного потока — successful_rps_in_window.
Для анализа основного окна использовать measure_start_epoch_ms/measure_end_epoch_ms
в result.json и timestamp в telemetry.jsonl; пики setup не приписывать переводам.
Разность pg-before/after охватывает весь запуск, включая setup и прогрев.
При Ctrl+C текущая ступень помечается INVALID.

Передать папки результатов **обоих** вариантов, включая smoke и неудачные ступени.
Результаты и архивы исходников игнорируются Git. Их не нужно коммитить.

Очистка только тестового проекта после завершения:

```bash
export MONOLITH_DIR=/home/basybemoog/golang_projects/bank-prototype
export COMPARISON_DIR=/home/basybemoog/bank_proto_microservice/load-tests/comparison
docker compose -p bank-course-comparison \
  -f "$COMPARISON_DIR/compose.mono.yml" -f "$COMPARISON_DIR/compose.micro.yml" \
  down --volumes --remove-orphans
```

## Старые и специальные тесты

Старые VU-сценарии load/stress/spike/full и их пакетный runner удалены.
Основная серия использует smoke/capacity/stress/spike из этого каталога.
run-capacity.sh сохранён для дополнительных замеров обычного стенда;
его результаты не объединяются с серией отчёта.
Idempotency/recovery/async/failover и `make reconcile` остаются проверками
микросервисных возможностей. Масштабирование gateway/nginx требует отдельного
контроля суммарного CPU и отдельной таблицы результатов.

## Что проверено при подготовке

Проверены разбор k6 inspect, Bash/Python syntax, Compose config и логика классификации
на искусственных метриках, детерминированный выбор операций и проверки ответов на заглушках. Банковские запросы, сборка Docker-образов, SQL-сверка
на живых БД и нагрузочные замеры при подготовке не запускались.
Первый общий smoke нужен также для проверки реального окружения запуска.
