# Ревью и границы сравнения

Дата: 05.10.2026. Проверены актуальные рабочие файлы обоих проектов, существующие
k6-сценарии и сохранённые результаты. Поскольку в репозиториях есть локальные
изменения, исторические логи не считаются результатом текущего исходного кода.

## Что нужно устранить до окончательных замеров

### P1: монолит возвращает устаревший список счетов после перевода

`bank-prototype/internal/services/account.go:73` кеширует список вместе с балансами;
`internal/cache/redis.go:77` задаёт TTL 300s.
`internal/services/transaction.go:241` удаляет кеш отдельных балансов при transfer,
но не списки обоих владельцев. Payment имеет аналогичную неполную инвалидацию
в `transaction.go:127`.

Последствие: HTTP 200 и быстрое чтение могут сопровождаться устаревшим балансом.
В микросервисах `internal/account/service/account_service.go:122` удаляет списки
обоих пользователей после применения перевода. Эти реализации дают разную свежесть.

Исправление должно охватить transfer и payment, выполняться после COMMIT и удалять
список отправителя и получателя. При асинхронном удалении нужно явно определить
допустимую задержку чтения; для текущего общего smoke требуется свежий ответ сразу
после успешного синхронного перевода. Заполнение кеша одновременно с инвалидацией
также требует отдельной проверки; удаление ключа само по себе не исключает эту гонку.
Код монолита в рамках подготовки тестов не изменялся.

### P1: порядок блокировок монолита допускает взаимоблокировки

`bank-prototype/internal/repository/transaction.go:44` сначала блокирует счёт
отправителя, затем получателя. При A→B и B→A порядок обратный.
Это возможность deadlock, подтверждаемая кодом; частота в текущем стенде требует
замера `pg_stat_database.deadlocks` и логов.
Micro блокирует пару по сортированным ID
(`internal/account/repository/account_repository.go:302`).
В новой методике взаимные переводы разрешены на обеих версиях; ошибки не считаются
успешными операциями, а deadlocks записываются до/после каждой ступени.

## Замечания монолита вне выбранной нагрузочной матрицы

### P1: закрытие счёта не атомарно

В `internal/services/account.go:212` читается баланс системного счёта,
затем отдельными запросами записывается новый баланс банка, обнуляется счёт
и меняется статус (строки 218, 224, 233).
Ошибка между запросами оставляет частично выполненное закрытие.
Два параллельных закрытия могут записать одинаковый устаревший баланс банка
и потерять одно зачисление; параллельный перевод также не сериализован с закрытием.
Нужна одна транзакция с блокировками и согласованный с переводами порядок блокировки.
Это вывод по коду; сценарий воспроизведения пока не запускался.

### P2: лимит пяти счетов проверяется отдельно от INSERT

`internal/services/account.go:46` считает активные счета,
а строка 57 создаёт новый отдельным запросом.
Несколько параллельных созданий могут одновременно пройти проверку.
Нужна сериализация создания по пользователю внутри одной транзакции.
Общий setup создаёт по одному счёту последовательно, поэтому этот дефект
не смешивается с измерением выбранного сценария.

## Ошибки прежних тестов

| Проблема | Последствие | Решение общего набора |
|---|---|---|
| Mono check принимает 201 или 400; micro allowlist иной | checks и http_req_failed имеют разные смыслы | общий expected 200/201; бизнес-успех проверяется отдельно |
| Mono full-scenario использует sharedUsers между VU | banking/read могут фактически ничего не делать | пользователи возвращаются из setup |
| Старый capacity verdict не требует успешных переводов | ступень с бизнес-отказами может стать OK | >=99% completed+валидный ответ и отдельный transfer rate |
| Сохранённые users переходят между RATE | меняются деньги, история и размер БД | чистые тома и setup на каждой ступени |
| Measure начинается до окончания gracefulStop прогрева | фазы конкурируют за ресурсы | отдельный промежуток для завершения прогрева |
| Runner собирает micro Compose даже при mono URL | чужие/пустые PG и Go метрики | отдельный явно выбранный профиль |
| docker stats читает все контейнеры без явной паузы | посторонние метрики и шум сборщика | только контейнеры проекта, период 5s |
| Прерывание не проверяется по exit code/полноте окна | оборванная ступень выглядит как SATURATED | INVALID, отдельные лог/код выхода/учёт итераций |

История также не сопоставима: micro учитывает limit/default pagination,
mono возвращает все операции. Даже одинаковый URL не задаёт одинаковый объём ответа.
Поэтому история остаётся в маленьком smoke, а не в общей нагрузочной матрице.

## Архитектурные и функциональные различия

- Монолит выполняет списание, зачисление, комиссию и журнал в одной SQL-транзакции.
  Micro пишет pending в transaction DB, применяет деньги локально в account DB,
  затем завершает запись; при сбоях работает recovery и идемпотентный журнал.
- Монолит использует float64 в Go и NUMERIC в БД. Micro — int64 копейки/BIGINT.
  Общий сценарий использует 1.00 рубль, чтобы исключить неодинаковое округление
  дробных комиссий. Паритет произвольных денежных значений этим не доказан.
- Монолит обновляет общий системный счёт на каждом переводе
  (`repository/transaction.go:94`). Micro переносит комиссии пакетами раз в 5s.
  Это потенциальный источник разницы; конкретную долю выигрыша без отдельного
  эксперимента приписывать этому изменению нельзя.
- Пулы PostgreSQL, Redis-клиенты, таймауты и обработка ошибок различаются.
  У монолита точный pgx default не задан в конфигурации; утверждение
  «всегда 12 соединений» по исходникам не подтверждено.
- Worker pool монолита в синхронных переводах удаляет кеш. Micro worker pool
  исполняет отдельный async endpoint. Число воркеров не задаёт параллелизм
  одинакового синхронного /transactions теста.
- У micro есть Idempotency-Key, окончательные отказы, pending/failed/recovery.
  Mono не предоставляет того же контракта повторов; сравниваются уникальные
  синхронные запросы с успешным completed, без искусственных сбоев.
- Закрытие счёта различается: mono переводит остаток банку и обнуляет его,
  micro меняет статус и сохраняет остаток. Полная эквивалентность бизнес-правил
  не установлена. Закрытие не входит в выбранную нагрузку.
- Mono для неизвестного transaction type выбирает transfer; micro валидирует
  список типов. Общий набор всегда передаёт явный допустимый тип.

Профили сравнения выравнивают общий CPU/RAM, toolchain, Redis persistence,
публичный вход и TTL списка счетов. Они не устраняют свойства реализации из списка
выше; эти свойства нужно назвать в отчёте.

## Что делать с уже имеющимися цифрами

Старые результаты сохранить как предварительные, но не объединять с новой матрицей:

- В pasted load/stress/full встречается около 48–49% http_req_failed при 100% checks.
  Без гистограммы кодов нельзя назвать эти запуски успешными или доказать причину.
  Нехватка денег при долгих переводах — гипотеза, а не установленный факт.
- В mono-low-r2 ступень 1000 содержит нулевые метрики и лог с interrupt signal.
  Это INVALID, а не измеренная нулевая производительность.
- В монотонной нагрузке есть немонотонные результаты: один RATE проходит,
  более низкий соседний не проходит. При малом числе повторов и дрейфе данных
  нельзя выделять точную границу.
- Для saved mono runs телеметрия PG/сервисов частично пустая из-за контекста Compose.
  На ней нельзя обосновывать конкретный bottleneck.
- Нельзя сравнивать один gateway с четырьмя как эксперимент «только nginx»:
  четыре реплики получают дополнительные CPU. Это отдельный эксперимент
  масштабирования с явно указанным бюджетом.

После нового запуска собрать одну таблицу по target × workload × RATE × repeat.
Отдельно показывать свежесть API, сверку БД, HTTP и бизнес-успех.
Выводы о задержках и устойчивой нагрузке строить по всем повторам.
Причины ограничений формулировать как гипотезы, пока их не подтвердит отдельная
смена одного параметра при остальных неизменных условиях.

## Проверки специфики микросервисов

Общий набор не заменяет saga/idempotency/recovery/failover tests.
Существующие интеграционные тесты и reconcile предназначены для этих свойств.
Их результаты образуют отдельный раздел: корректность распределённой системы
при неизвестном исходе/повторе/восстановлении, а не HTTP RPS против монолита.
